# Adaptive energy and accessibility mode

Use this mode when attention, fatigue, chronic illness, disability, stress,
sensory load, or environment changes available capacity. The objective remains
the same; timing, representation, interaction, and scaffolding adapt.

## Choose today's capacity

### Green — normal capacity

Build a 60–90 minute vertical slice, perform a debug hunt, or complete an
independent transfer task.

### Yellow — limited capacity

Use two 20–25 minute units. Choose one bounded artifact: failing test, small
domain rule, diagram, review, query fixture, accessible component state, or
runbook correction.

### Red — recovery capacity

Use 5–15 minutes without pretending it is a full build session. Retrieve three
concepts aloud, inspect one small diff, label a worked example, update a diagram,
or organize the next ready task. Stop if the activity worsens capacity.

Red work preserves continuity; it does not count as project evidence until
later verified and transferred.

## Access options

- Use text, code, diagram, narration, or tactile/paper modeling as an entry point.
- Use keyboard-only workflows, screen readers, zoom, contrast, reduced motion,
  text-to-speech, speech-to-text, or alternate input as needed.
- Reduce split attention: keep requirement, example, and relevant code adjacent.
- Prefer narrow files, explicit names, small functions, and visible state over
  clever compression.
- Make timers optional; use artifact-based stop conditions when time pressure harms focus.
- Save restart notes: current fact, next action, command to run, and open risk.

## Restart protocol

```text
Outcome I was pursuing:
Last verified fact:
Current failing/passing command:
Next physical action under 10 minutes:
Do not investigate yet:
```

Write this before any forced stop. On return, run the recorded command before
trusting memory.

## Adapt a mastery exercise

Preserve the same capability while changing load. Break a 30-task bank into
one task per day; use a diagram or narration before code; provide a faded
example at low capacity; complete the independent version later. Record whether
the barrier was knowledge, interface access, working memory, or energy.

## Adapt a project increment

Maintain a ready queue with Green, Yellow, and Red tasks. Examples:

- Green: concurrency-safe command across API and database.
- Yellow: authorization decision table plus two integration tests.
- Red: annotate one state transition or improve restart/runbook notes.

Do not let the Red queue become only documentation cleanup; it should support
future engineering work.

## AI role

Ask AI to reduce task granularity, summarize only the currently relevant files,
turn voice notes into a checklist, or quiz using one question at a time. Require
it to preserve acceptance criteria and label deferred risk. Do not let it finish
the implementation merely because capacity is low.

## Failure signals and correction

- **Repeated overextension/crash:** plan from sustainable Yellow capacity.
- **Scaffold never fades:** schedule independent verification on the next Green day.
- **Reduced scope removes the core risk:** split delivery, not correctness.
- **Accessibility tool conflicts with the app/course:** record the barrier as a
  product defect and add it to the test strategy.
- **Shame-based backlog:** track evidence and recovery, not hours or streak purity.

## Exit evidence

Keep capacity/mode choice, completed artifact, restart note, later independent
verification, and any accessibility barrier converted into a reusable design rule.
