# 17 · EF Core Fundamentals

Entity Framework Core is the default way .NET talks to a relational database.
It is an ORM, which means it is doing two jobs at once: translating your LINQ
into SQL, and tracking objects in memory so it knows what to write back. Most
EF surprises — the slow query, the update that didn't save, the update that
saved something you didn't expect — come from misunderstanding one of those
two jobs.

Every exercise here runs against a **real SQLite database held in memory**.
Real SQL, real constraints, real transactions, nothing written to your disk.

## The mental model

**1. A `DbContext` is a unit of work plus a set of tables.**

```csharp
public class ShopDb(DbContextOptions<ShopDb> options) : DbContext(options) {
    public DbSet<Product> Products => Set<Product>();
}
```

Conventions do the schema: a property named `Id` (or `ProductId`) becomes the
primary key, and an integer key is generated by the database.

**2. Nothing hits the database until `SaveChanges`.**

```csharp
db.Products.Add(p);     // staged in the change tracker
db.SaveChanges();       // one INSERT, in a transaction
```

After the save, EF writes the generated key back onto *your* object — no
re-query needed.

**3. `IQueryable` is a query being built; `IEnumerable` is data in your
process.**

```csharp
db.Products.Where(p => p.Price > 10).ToList()   // WHERE runs in SQL
db.Products.ToList().Where(p => p.Price > 10)   // loads EVERY row, then filters
```

Where you put `.ToList()` is the single most consequential decision in an EF
query. Everything before it becomes SQL; everything after it runs on data
already dragged across the wire.

**4. Tracked entities save themselves.**

EF snapshots the original values on load and diffs at `SaveChanges`:

```csharp
var p = db.Products.Find(id);
p.Price = 5m;
db.SaveChanges();          // UPDATE ... SET Price = 5 — no Update() call
```

`db.Products.Update(p)` also works but marks *every* property modified,
writing columns nobody touched.

**5. `AsNoTracking()` for reads you will not write back.**

No snapshot, less memory — and edits to the result go nowhere at all.
Projecting with `Select` into a DTO opts out of tracking automatically, since
there is no entity to write back.

## The details that bite

1. **`SaveChanges` in a loop is n round trips and n transactions.** Use
   `AddRange` + one save.

2. **`Count()` vs `ToList().Count`.** The first is `SELECT COUNT(*)`; the
   second fetches every row. Same answer, wildly different cost.

3. **`Any()` beats `Count() > 0`.** It becomes `SELECT EXISTS(...)` and stops
   at the first match.

4. **`Single` throws on duplicates; `First` doesn't.** Use `Single` when more
   than one row would be a bug — it turns a broken assumption into a loud
   error instead of an arbitrary row.

5. **Project *before* materialising.** `.Select(...).ToListAsync()` fetches
   three columns; `.ToListAsync().Select(...)` fetches all of them.

6. **Never serialise entities to clients.** An entity is your storage shape; a
   DTO is your wire contract. Returning the entity publishes your schema and
   leaks columns (`Stock`, `PasswordHash`, `IsAdmin`) you never meant to send.

7. **`AddDbContext` registers *scoped*, and that is correct.** One context per
   request. A singleton `DbContext` is not thread-safe, shares a change
   tracker between users, and grows forever.

8. **You cannot resolve a scoped service from the root provider.** Use
   `app.Services.CreateScope()` when seeding at startup. That restriction is
   the framework protecting you.

9. **SQLite has no decimal type.** EF stores decimals as TEXT to keep them
   exact, which means SQLite cannot `SUM` them server-side. On SQL Server the
   same LINQ translates fully. "LINQ is provider-independent" has edges, and
   the compiler will not warn you about them.

10. **Use the async methods** — `ToListAsync`, `FindAsync`,
    `SaveChangesAsync`. A request thread blocked on I/O is a thread not
    serving anyone.

## Cheat table

| You want | Write |
| --- | --- |
| All matching rows | `.Where(...).ToListAsync()` |
| One row by key | `.FindAsync(id)` (checks the tracker first) |
| One row by predicate | `.SingleOrDefaultAsync(p => ...)` |
| Does anything match? | `.AnyAsync(p => ...)` |
| How many? | `.CountAsync()` |
| Read-only query | `.AsNoTracking()` |
| Only some columns | `.Select(p => new Dto(...))` |
| Insert many | `.AddRange(...)` then one `SaveChangesAsync()` |
| Update | load, mutate, `SaveChangesAsync()` |
| What will EF do? | `db.Entry(e).State`, `db.ChangeTracker.Entries()` |
